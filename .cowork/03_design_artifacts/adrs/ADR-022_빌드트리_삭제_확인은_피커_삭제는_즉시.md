# ADR-022 — Delete Build Tree: 확인은 QuickPick, 삭제는 휴지통 없이 즉시

## ADR ID
`ADR-022`

## 제목
`devSwitcher.deleteBuildTree`의 확인 UI를 **모달 → QuickPick(`canPickMany`, 전 항목 기본 체크)** 으로 바꾸고, 삭제는 **휴지통을 거치지 않고 즉시** 수행한다. 확인 자체는 `devSwitcher.confirmDeleteBuildTree`(기본 `true`)로 끌 수 있다. 이로써 확장 코드에서 `modal: true`는 **0건**이 된다.

## 상태
`Accepted`

## 날짜
2026-08-26

---

## Context (맥락)

v1.3.0 F5 검증(세션 #019)에서 Delete Build Tree는 기능적으로 통과했으나, 세션 #020에서 Human이 **UI 자체**를 문제 삼았다: "이 메시지박스 쿨하지 않다. 다른 방법이나, 안 뜨고 처리하면 안 되나."

실태 조사 결과:

- **`modal: true`는 전체 코드에서 2곳뿐**이었고 둘 다 이 흐름이었다(삭제 확인 / 휴지통 실패 시 영구삭제 재확인). 나머지 64건은 화면을 막지 않는 토스트다.
- 반면 **QuickPick은 11곳** — 칩, 프로젝트 전환, 그룹, Doctor, 마법사, 그리고 **Clean의 범위 선택**까지 모든 선택이 피커에서 이뤄진다.
- 즉 문제는 개수가 아니라 **일관성**이었다. 세션 #019에서 Clean/Delete를 같은 데이터 모델(`CleanScope[]` / `BuildTreeDir[]`)로 맞춰놓고 **UI만 짝이 안 맞은 채** 남아 있었다.
- 모달 버튼 라벨은 **VSCode 로케일**을 따르고 우리 액션 라벨은 영문이라 `Delete` / `취소`로 **언어가 섞여** 표시됐다. 우리가 고칠 수 없는 종류의 결함이며, 모달을 쓰지 않으면 사라진다.

이어진 F5(세션 #020)에서 두 번째 사실이 드러났다. dotnet 픽스처 삭제 중 **Windows 셸이 "이 폴더를 삭제하려면 관리자 권한이 필요합니다"** 모달을 띄웠다. 파일시스템 증거로 원인을 규명했다(KB #13·#15 절차):

| 증거 | 값 |
|------|-----|
| `bin`·`obj` 생성 시각 | 20:50:35 — 삭제됐다가 **재생성됨** |
| 같은 초의 신규 프로세스 | `MSBuild.dll /nodemode:1` PID 31536, **20:50:35** |
| 그 부모 | `ms-dotnettools.csdevkit-3.20.199`의 `visualstudio-projectsystem-buildhost` |
| obj ACL | 현재 사용자 **FullControl** — 실제 권한 문제 없음 |

**C# Dev Kit의 design-time build가 삭제 중인 디렉토리에 쓰고 있었다.** 셸은 이 `ACCESS_DENIED`를 "관리자 권한" 메시지로 표시한다. 그리고 그 대화상자는 **`useTrash: true`가 부른 것**이다 — 휴지통 삭제는 Electron `shell.trashItem` → Windows `IFileOperation`으로 내려가고, 셸은 충돌 시 자기 UI를 띄운다. **우리 모달을 없앴더니 OS가 자기 것을 올린 셈**이었다.

## Decision (결정)

### 1. 확인 UI = QuickPick (`canPickMany`, 전 항목 기본 체크)

`describeDeletionPrompt`(모달 본문 문자열 조립)를 폐기하고 `describeDeletionTitle` + `buildDeletionItems`로 대체한다. 순수 함수·vscode 무의존은 유지(coding_convention pure/IO 분리).

**단일 선택 피커(Clean과 동형)를 쓰지 않은 이유**: 어댑터별 `buildTreeDirs` 반환 개수를 전수 확인한 결과 cargo·cmake는 1개지만 **dotnet은 `bin`·`obj` 2개**다. 단일 선택으로 만들면 .NET 사용자가 같은 명령을 두 번 실행해야 한다.

`canPickMany` + 전 항목 기본 체크는 모달의 all-or-nothing을 그대로 보존하면서(Enter = 전부 삭제) **모달이 못 하던 일**을 더한다 — 체크를 풀면 그 항목만 남는다. "obj만 지우고 restore 결과는 남기기"가 취소 후 터미널 대신 스페이스바 한 번이 된다.

### 2. 삭제는 휴지통 없이 즉시 (`useTrash: false`)

Human 근거(세션 #020): **"개발자들 대부분 삭제 이유는 다시 빌드하고 싶어서다. 백업해야 할 데이터가 있다면 삭제 전에 먼저 해놓고 지운다."**

- 지우는 대상은 **정의상 재생성 가능한 산출물**이고, 지우는 **동기 자체가 재생성**이다. 그 시점에 내용물의 가치는 0이다.
- 다른 한 동기인 **디스크 회수를 휴지통이 정면으로 방해한다** — 수 GB짜리 `target/`을 휴지통에 넣으면 비우기 전까지 공간이 그대로다.
- 휴지통을 안 쓰면 **셸을 경유하지 않으므로 OS 대화상자가 아예 발생하지 않는다.** 잠긴 파일은 우리에게 에러로 올라오고, 우리 문구로 보고한다.
- **안전망을 사후 → 사전으로 옮긴다.** 확인 피커(기본 켜짐)와 `classifyDeletions`의 경로 가드가 그 역할을 한다. 휴지통은 "무엇을 지우는지 모르고 눌렀을 때"의 보험인데, 이 명령은 그걸 이미 앞단에서 막는다.

### 3. 확인 자체를 끄는 설정

`devSwitcher.confirmDeleteBuildTree`(기본 `true`). VSCode 자신의 `explorer.confirmDelete` 관례를 따른다. 꺼도 **경로 가드는 그대로** 적용된다 — 가드는 *잘못된 경로*를 막는 장치이지 *의도한 삭제*를 막는 장치가 아니기 때문이다.

파괴적 동작의 기본값까지 무확인으로 두는 것은 AI가 1회 우려를 표명했고, Human이 **기본 확인 유지 + 옵트인 해제**로 합의했다.

### 4. 휴지통 실패 fallback 제거

2번의 부수 효과로 "휴지통 실패 → 영구삭제 재확인" 분기가 통째로 사라진다. **이 분기에 결함이 하나 있었다**: 사용자가 영구삭제를 거절하면 `continue`로 건너뛰는데 `failed`에 아무것도 쌓이지 않아, 루프 종료 후 `deleted the build tree`라는 **성공 메시지가 나갔다**. 디렉토리는 그대로 있는데 지웠다고 보고한 것이다.

세션 #019 버그 #3과 같은 계열 — *안전장치가 형식만 남고 실질을 잃은 경우*. 묻는 것까지는 옳았으나 그 대답을 결과 보고에 반영하지 않았다. 분기 제거로 결함도 함께 사라진다.

## Consequences (결과)

- (+) 확장 전체에서 `modal: true` **0건**. 모든 선택이 피커에서 이뤄진다(INV-2 UI 일관성).
- (+) 버튼 라벨 언어 혼용(`Delete` / `취소`) 소멸.
- (+) `.NET`에서 `bin`/`obj` 부분 삭제가 가능해졌다 — 모달로는 불가능하던 동작.
- (+) Windows 셸 대화상자가 발생하지 않는다. 실패는 우리 토스트로, 우리 문구로 보고된다.
- (+) 디스크가 실제로 회수된다.
- (+) 오보고 결함(건너뜀을 성공으로 보고) 제거.
- (−) **복구 불가.** 휴지통이라는 사후 보험이 없어졌다. 확인 피커를 끈 사용자는 안전망이 경로 가드뿐이다 — 옵트인이므로 수용.
- (−) C# Dev Kit이 `obj/`를 즉시 재생성하는 현상은 **여전하다**(우리 통제 밖). 기능이 고장 난 것처럼 보일 수 있어 사용자 문서에 명시한다.
- (−) `describeDeletionPrompt` 폐기로 관련 단위 테스트 3건을 6건으로 교체했다.
