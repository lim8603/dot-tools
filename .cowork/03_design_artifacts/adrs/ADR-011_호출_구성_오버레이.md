# ADR-011 — 호출 구성 오버레이 (Invocation Config Overlay)

## ADR ID
`ADR-011`

## 제목
컴파일 옵션·출력·링커·환경변수·빌드 전후 이벤트를 캐노니컬 파일 편집 없이 `(프로젝트 × 구성)`별 "호출 구성 오버레이"로 저장하고, 빌드/실행 호출 시 `--config`/env/flag로 주입한다. 캐노니컬 파일 편집은 v2로 이월한다.

## 상태
`Accepted`

## 날짜
2026-08-15

---

## ADR 필요성 판단

- 제약·확장성: 설정 저장 모델(파일 소유 vs 오버레이)과 데이터 스키마(profile 차원)를 장기적으로 규정한다.
- 비용: v1에서 파일 파서/라인 편집(구 §8.7)을 걷어내고 호출 시점 주입으로 대체 — 구현 비용·리스크를 이동시킨다.
- 보안: 빌드 전후 이벤트가 사용자 자유 명령(셸) 실행 표면을 연다 → NFR-002의 문서화된 예외가 필요하다.
- 세 축이 얽혀 ADR로 남긴다.

---

## Context (맥락)

VS2026식 "프로젝트 속성"(출력 위치/이름, 인클루드 폴더, 컴파일러/링커 옵션, 빌드 전후 이벤트)을 어디까지 지원할지 검토했다. 초기 설계(구 §8.7, F4/ADR-007)는 v1에서 `Cargo.toml [profile.*]` 스칼라 키를 라인 단위로 국소 편집하도록 했다.

그러나 세 가지가 드러났다.
1. **대부분의 빌드 옵션은 호출 시점 주입이 가능**하다 — cargo는 `--config KEY=VAL`(Rust 1.63+)과 환경변수(`RUSTFLAGS`·`CARGO_TARGET_DIR`)로 프로필·빌드·타깃 설정을 파일 수정 없이 덮어쓸 수 있다. dotnet은 `-p:`, cmake는 `-D`로 동일하다.
2. **VS의 configuration(Debug/Release/커스텀)은 (프로젝트 × 구성)별로 값이 달라야** 하는데, 현재 `PersistedState.runArgs`는 `projectId` 단위라 구성(profile) 차원이 없다.
3. 확장이 캐노니컬 파일을 **고쳐 쓰는 것은 SSOT(ADR-007) 정신과 긴장**한다.

사용자 통찰(세션 #002): "우리는 중계지만, CMD 호출 시 명령·옵션을 저장해뒀다가 대신 넣어줄 수 있다." 이는 파일 편집이 아니라 **호출 조립**이며, 이미 F16(runArgs)이 하는 패턴이다.

---

## Decision Drivers (결정 요인)

- SSOT 유지: 캐노니컬 파일을 소유·재작성하지 않는다.
- VS식 `(프로젝트 × 구성)` 매트릭스 지원.
- v1 구현 단순화: 파서/라인 편집 제거.
- 투명성: 실제 실행될 명령을 사용자에게 보여줄 수 있어야 한다.

---

## Options Considered (검토한 옵션)

### Option A: 캐노니컬 파일 국소 편집 (기존 §8.7) — 기각(→ v2 이월)
- 장점: 수동 CLI 빌드에도 적용된다(파일이 진실).
- 단점: 파일 소유/파괴 위험, 파서 필요, 구성 차원 표현이 어렵고, SSOT와 긴장.

### Option B: 호출 구성 오버레이 (workspaceState + `--config`/env 주입) — 채택
- 장점: 파일 무편집, `(project × profile)` 자연 표현, SSOT 유지, 구현 단순, 명령 미리보기 가능.
- 단점: DevSwitcher 호출 경로에서만 적용(수동 CLI엔 미적용), `RUSTFLAGS` 재빌드·비병합 주의.

### Option C: `.cargo/config.toml` 편집
- 장점: cargo가 직접 읽는다.
- 단점: 새 파일 소유, 구성별 분기가 어렵고(디렉터리 단위), 여전히 파일 편집이다.

---

## Decision (결정)

**Option B** — "호출 구성 오버레이"를 도입한다.

- **3계층 분리**:
  - ① **확장 설정** — `settings.json`(`contributes.configuration`). 확장 동작(scan.exclude 등). 스코프: 확장/워크스페이스 전역.
  - ② **프로필 정의 (SSOT)** — 캐노니컬 파일(`Cargo.toml` 등). `opt-level`·`lto`·features·bin 이름 등 "프로젝트의 진실". v1은 **읽기만**.
  - ③ **호출 구성 오버레이 (신규)** — `workspaceState`. RUSTFLAGS·출력경로·링커·env·runArgs·전후명령. DevSwitcher 호출 시에만 적용.
- **키**: 오버레이는 `(projectId × profile)` 단위. 구성(profile) 목록은 ②(캐노니컬)에서 읽어와 우리가 지어내지 않는다.
- **주입**: 어댑터가 빌드/실행 Task를 조립할 때 오버레이를 **언어별 메커니즘으로 접어 넣는다**(cargo `--config`/env, dotnet `-p:`, cmake `-D`, python env). 파일 미편집. 주입 시점(configure/build/run)은 어댑터가 소유한다.
- **투명성**: 적용될 최종 명령을 설정 페이지 하단에 미리보기로 노출한다(ADR-012).
- **v1/v2**: v1 = 읽기 + 오버레이 주입. **캐노니컬 파일 편집(구 §8.7)은 v2로 이월** — v2는 "오버레이를 파일에 영구 반영(승격)" 기능으로 정의한다.
- **빌드 전/후 이벤트**: 저장된 사용자 명령을 pre/post Task로 실행(BAT처럼 호출만). 자유 명령이라 `ShellExecution` 허용 = NFR-002의 **문서화된 예외**.

---

## Consequences (결과)

### 긍정적
- SSOT를 유지하면서 VS식 `(프로젝트 × 구성)` 속성을 제공한다.
- v1에서 파서/라인 편집을 제거 → 구현·리스크 감소.
- 언어별 주입 시점 차이를 어댑터가 흡수 → UI 무지 유지(INV-2).
- 명령 미리보기로 "중계" 투명성 확보.

### 부정적 / Trade-off
- 오버레이 값은 DevSwitcher 호출에만 적용된다(수동 CLI 미적용) — 설계된 동작이나 사용자 안내 필요.
- `RUSTFLAGS`/env 주입은 전체 재빌드를 유발하고 `.cargo/config.toml`의 rustflags와 병합되지 않는다(env 우선) → 안내 필요.
- 빌드 전후 이벤트 = 임의 명령 실행 표면 → 셸 예외를 NFR-002에 명시.
- `PersistedState` 스키마에 profile 차원 추가 → data_model 변경(기존 runArgs 승격).
