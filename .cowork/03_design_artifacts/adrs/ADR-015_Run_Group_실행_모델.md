# ADR-015 — Run Group 실행 모델 (준비=프로세스 시작, 계층적 위상정렬)

## ADR ID
`ADR-015`

## 제목
Run Group(C-6)은 여러 프로젝트를 **종속 순서대로 일괄 기동**한다. 멤버는 **Run 전용**(장기 실행 서비스)이며, 그룹은 `dependsOn` 그래프를 **계층적 위상정렬**(Kahn)해 **계층 단위로 기동**한다(같은 계층은 병렬, 다음 계층은 이전 계층이 전부 "준비"된 뒤). **"준비" 신호 = 멤버 태스크의 프로세스 시작**(`onDidStartTaskProcess`)이며 프로세스 종료가 아니다 — 서비스는 종료되지 않기 때문이다. 정리(teardown)는 기동된 `TaskExecution`을 종료한다. 그룹 정의는 `workspaceState`(`PersistedState.groups`)에 저장한다(ADR-001). 포트/헬스체크 기반 준비 감지는 **후속 마이너**(TASK-039)로 분리한다.

## 상태
`Accepted`

## 날짜
2026-08-17

---

## ADR 필요성 판단

- 제약·확장성: 기존 실행 모델(`TaskRunner.run`은 **프로세스 종료코드**를 판정)과 근본적으로 다른 **장기 실행·준비 기반 전진** 모델을 도입한다. 그룹의 실행 프리미티브·상태 소유·정리 방식을 장기적으로 규정한다.
- 운영 영향: 여러 프로젝트를 동시에 기동/정리하는 새 실행 경로가 코어에 추가된다. 준비 신호 정의(프로세스 시작 vs 헬스체크)가 v1.0.0 범위와 사용자 경험을 가른다.
- 두 축 이상이 얽히고 되돌리기 어려운 결정 → ADR로 남긴다.

---

## Context (맥락)

MS-013은 INT-001의 마지막 완료 조건인 **C-6 Run Group**을 구현한다. 목표는 여러 프로젝트를 하나의 그룹으로 묶어 **종속 순서대로 일괄 기동/정리**하는 것이다(예: `auth → api → web`).

기존 액션(빌드/실행/디버그)은 [`TaskRunner.run`](../../../src/core/taskRunner.ts)이 **`onDidEndTaskProcess`(프로세스 종료)** 를 기다려 종료코드를 판정하는 **일회성(one-shot)** 모델이다. 그러나 그룹 멤버는 대부분 **장기 실행 서비스**(웹 서버 등)로 **종료되지 않는다**. 이 모델로 멤버를 순차 `await`하면 첫 서비스에서 영원히 블록된다. 따라서 그룹 실행은 **"시작 → 준비되면 다음 진행"** 이라는 다른 프리미티브가 필요하다 — *종료*가 아니라 *준비*가 종속 체인을 전진시킨다.

또한 "준비"를 무엇으로 판정할지는 제품 결정이다: (a) 프로세스가 뜬 순간(단순·범용) vs (b) 포트 open/HTTP 200(정확하지만 멤버별 헬스 설정 UI 필요). 이 선택이 v1.0.0 범위를 좌우한다.

---

## Decision Drivers (결정 요인)

- **아키텍처 일관성** — 그룹은 어댑터의 기존 `createRunTask`(언어별 실행 Task)를 재사용해 기동한다. 어댑터/UI는 그룹을 모른다(BR-003, INV-2). 오케스트레이션만 새 계층이다.
- **프로세스별 락 재사용** — 그룹 멤버 기동은 `TaskRunner`의 **프로젝트별 락**을 재사용해 한 프로젝트가 그룹과 개별 실행에서 중복 기동되지 않도록 한다(E9).
- **파일 무편집 불변식(ADR-013)** — 그룹 정의는 `workspaceState`에만 저장한다. 어떤 캐노니컬/설정 파일도 편집하지 않는다.
- **의존 최소화·점진 범위(ADR-009)** — 준비 감지를 "프로세스 시작"으로 시작하면 외부 의존(포트 스캐너·HTTP 클라이언트)·멤버별 설정 UI 없이 v1을 낼 수 있다. 헬스체크는 가치가 크지만 범위가 커서 후속 마이너로 분리한다.
- **저장 일관성(ADR-001)** — 선택/오버레이와 같은 `PersistedState`에 그룹을 추가(additive)해 저장·재개 경로를 재사용한다.

---

## Options Considered (검토한 옵션)

### 준비(전진) 신호

- **Option A — 프로세스 시작 감지 (채택)**: 멤버 Task를 기동하고 `onDidStartTaskProcess`가 뜨면 즉시 다음 계층 진행. 장점: 단순·범용·무의존, v1.0.0을 빠르게. 단점: "서비스가 실제 요청을 받을 준비"까지는 보장 못 함(느린 부팅은 후속 헬스체크로).
- **Option B — 헬스체크 (후속 마이너, TASK-039)**: 포트 open/HTTP 200까지 대기. 장점: 실서비스 `depends_on`에 정확. 단점: 멤버별 준비 조건(포트·URL·타임아웃) 설정 UI·구현 필요 → v1.0.0 범위 확대.
- **Option C — 고정 지연(stagger)**: 시작 후 N초 대기. 단순하나 부정확(느린 서비스 놓침·빠른 서비스 과대기). 임시 방편.

### 실행 순서

- **Option A — 계층적 위상정렬 (채택)**: `dependsOn`을 Kahn 알고리즘으로 계층화 — 같은 계층은 병렬, 다음 계층은 이전 계층 전부 준비 후. 종속을 정확히 지키면서 독립 브랜치를 병렬화.
- **Option B — 순수 순차**: 선언 순서대로 하나씩. 구현 단순하나 독립 서비스도 직렬화돼 느리고, 종속을 사용자가 수동 정렬해야 함.

## Decision (결정)

**준비=Option A(프로세스 시작) + 순서=Option A(계층적 위상정렬)**. 세부:

- **모델(TASK-036, 순수)**: `RunGroup { id, name, members }`, `RunGroupMember { projectId, dependsOn[] }`. **Run 전용** — 멤버는 서비스 기동이며 빌드가 필요하면 어댑터의 `runRequiresBuild`가 이미 처리한다(그룹 모델에 build/debug 멤버 없음). 저장은 `PersistedState.groups`(`workspaceState`, ADR-001) — **additive 필드**라 MS-013 이전 상태는 `groups` 부재 → `StateStore`가 로드시 `[]`로 정규화. 그룹은 워크스페이스-로컬 오케스트레이션이므로 **프로파일 export(F12)에는 미포함**(v1).
- **계획 도출(TASK-036, 순수)**: `core/runGroupPlan.ts` — `planGroupExecution(group): { layers, cycle? }`(계층적 위상정렬, cyclic 시 진행 가능한 접두부만 배치 후 잔여를 `cycle`로 보고) + `validateGroup(group)`(빈 그룹·중복 멤버·자기종속·dangling·cycle 검출). vscode-free 순수 함수라 단위테스트 대상.
- **실행(TASK-037)**: `GroupOrchestrator`가 계획의 `layers`를 순서대로 기동. 각 멤버는 어댑터 `createRunTask`로 만든 Task를 **종료 대기 없이 시작**하고 **프로세스 시작 시점에 다음으로 전진**한다. → `TaskRunner`에 기존 `run`(종료 대기)과 별도로 **"시작 + 실행 추적 + 시작 시점 resolve" 프리미티브**를 추가하되 **프로젝트별 락은 공유**한다. 정리(teardown)는 추적한 `TaskExecution`을 종료한다.
- **트리거/정의 UI(TASK-038)**: 설정 페이지 그룹 탭(정의 편집) + 그룹 QuickPick·상태바 진입점(기동/정리). UI는 어댑터/언어를 모른 채 그룹·멤버·종속만 다룬다.
- **준비 감지(TASK-039, 후속 마이너)**: 포트/헬스체크를 멤버별 옵션으로. v1.0.0 범위 밖 — 프로세스 시작 감지로 충분한 다수 시나리오를 먼저 커버.
- **버전 정책**: MS-013 완주는 INT-001의 등록 조건(C-7+C-6)을 모두 충족하지만 **자동으로 v1.0.0을 트리거하지 않는다**. Run Group은 **v0.4.0**으로 배포하고, **v1.0.0 완주 선언은 추가 기능·논의(TASK-042)에서 Human이 명시적으로 결정**한다(프로젝트 결정 D-19). SemVer: 0.3.0 → 0.4.0(C-6) → (추가 기능) → 1.0.0(Human 선언 시).

## Consequences (결과)

### 긍정적
- 어댑터/UI 무변경으로 다언어 그룹이 동작(INV-2 재확인) — 그룹은 순수 오케스트레이션 계층.
- 준비=프로세스 시작이라 외부 의존·멤버별 설정 없이 v1 출하. 헬스체크는 계약을 깨지 않고 후속에 추가 가능(멤버 옵션 확장).
- 계층적 위상정렬로 종속 정확성과 병렬성(독립 브랜치)을 동시에.
- `workspaceState` additive 저장으로 기존 상태와 호환·재개.

### 부정적 / Trade-off
- 프로세스 시작 ≠ 서비스 준비 완료 — 부팅이 느린 서비스는 의존 서비스가 아직 못 받을 수 있다(후속 헬스체크로 보완, 그전엔 사용자가 순서/지연 인지 필요).
- `TaskRunner`에 두 실행 프리미티브(종료 대기 / 시작 추적)가 공존 → 락 공유·정리 책임을 명확히 유지해야 한다.
- 그룹은 export 미포함이라 클론 간 공유가 안 됨(v1 의도적 범위; 필요 시 후속에 그룹 export 추가).
