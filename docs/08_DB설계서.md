> **이 프로젝트는 DB를 사용하지 않는다.**
> 모든 영속 상태는 VSCode `workspaceState`(Memento) 기반으로 저장한다(ADR-001).
> 값의 원본(프로필 정의 등)은 각 언어의 캐노니컬 파일(SSOT)이며, 확장은 이를 읽기만 한다(ADR-007, ADR-013).
> 본 문서는 전통적 DB 설계서를 대체하여 **데이터 저장 설계**를 기록한다.

## 1. 저장 아키텍처 개요

- **DB 미사용**: RDBMS·NoSQL·파일 DB 일절 없음. 저장 대상은 "사용자의 선택 상태 + 호출 오버레이 + Run Group 정의"뿐이며 규모가 작아(프로젝트 수 × 칩 수) Memento(JSON 직렬화)로 충분하다(ASM-001).
- **저장 위치**: `context.workspaceState`(VSCode Memento) — 기계 로컬·워크스페이스별 저장. `settings.json` 저장안은 기각됨(`.vscode/` 커밋 시 개인 상태가 팀 diff를 오염시키는 문제, ADR-001).
- **값이 아니라 선택만 저장**: 프로필 정의(`opt-level`·`lto`·features 목록 등)는 각 언어 캐노니컬 파일에만 존재하고, 확장은 사용자가 무엇을 골랐는지(선택)와 호출 시 덧입힐 오버레이만 저장한다(ADR-007, ADR-011).
- **캐노니컬 파일 무편집**: 확장은 사용자의 빌드 파일(`Cargo.toml` 등)을 절대 편집하지 않는다 — 영구 불변식(ADR-013).
- **공유는 export/import로만**: `workspaceState`는 클론 간 자동 공유되지 않으며(의도된 트레이드오프), 공유가 필요할 때 `devswitcher.profile.json` export/import(F12)를 사용한다.

## 2. 설정의 3계층 (ADR-011)

설정은 소유·목적이 다른 세 계층으로 분리된다. 혼동 방지를 위해 저장 위치와 스코프를 명시한다.

| 계층 | 무엇 | 저장 위치 | 스코프 | 수동 CLI에도 적용 |
|------|------|----------|--------|------------------|
| ① 확장 설정 | 확장 동작(`scan.exclude`·`statusBar.abbreviate`) | `settings.json` (`contributes.configuration`) | 확장/워크스페이스 전역 | — |
| ② 프로필 정의 (SSOT) | `opt-level`·`lto`·features·bin 이름 = "프로젝트의 진실" | 캐노니컬 파일(`Cargo.toml` 등) | (프로젝트 × 구성) | 적용됨 — 네이티브 도구가 직접 읽음 |
| ③ 호출 구성 오버레이 | 컴파일러/링커 옵션·출력경로·env·runArgs·전후명령 | `workspaceState` — `(projectId × profile)`별 | (프로젝트 × 구성) | 미적용 — DevSwitcher 호출 시에만 |

- ①↔③은 완전 별개(저장소·목적·스코프 상이). ②↔③은 `(프로젝트 × 구성)` 키를 공유해 설정 페이지에서 함께 표시하되, ②는 읽기·③은 편집이다.
- v1은 ②를 **읽기만** 하고, ③ 오버레이 주입으로 VS식 속성을 제공한다. ②의 파일 편집은 v2로 이월.

## 3. 저장소 구성

| 데이터 | 저장 위치 | 근거 |
|--------|----------|------|
| 선택 상태(프로파일·아키텍처·features·타깃 등 칩 값) | `context.workspaceState` — 키 `devSwitcher.state.v1` | ADR-001 |
| 호출 구성 오버레이 (계층 ③) | 동일 키 내 `invocation` — `(projectId × profile)`별 | ADR-011 |
| Run Group 정의 | 동일 키 내 `groups` — 워크스페이스 로컬 | ADR-015 *(구현 반영: v0.4.0/MS-013 additive 추가)* |
| 프로파일·features 등 값의 정의 (계층 ②) | 각 언어 캐노니컬 파일 (§6) | ADR-007 (SSOT) |
| 동작 설정 (계층 ①) | `settings.json` (default 보유) | 상세설계서 §14 |
| 옵션 카탈로그(설명·예제·허용값) | 확장 번들 데이터(어댑터별 `OptionSpec[]`, 읽기 전용) | ADR-012 |
| 공유 스냅샷 | `devswitcher.profile.json` (export/import, 선택적) | F12, §5 |
| 감지된 프로젝트 목록 | **저장 안 함** — 매 활성화 시 재스캔이 원천 | 상세설계서 §6.1 |

## 4. 스키마 정의 — `PersistedState` (workspaceState)

저장 키: `devSwitcher.state.v1` (`src/core/types.ts`의 상수 `PERSISTED_STATE_KEY`)

### 4.1 최상위 구조

> 아래 타입은 `src/core/types.ts` 기준이다. 기준 문서 `data_model.md` §2의 스키마에는
> `groups` 필드가 없으나, **구현 반영**: Run Group(MS-013, v0.4.0)에서 additive로 추가되었다.

```ts
interface PersistedState {
  activeProjectId?: string;
  /** projectId -> (chipId -> value); profile 칩 포함 */
  selections: Record<string, Record<string, ChipValue>>;
  /** 계층 ③ 오버레이 — projectId -> profileName -> InvocationConfig (ADR-011) */
  invocation: Record<string, Record<string, InvocationConfig>>;
  /** Run Group 정의 (구현 반영: MS-013 additive — 이전 상태엔 없어 로드 시 []로 정규화) */
  groups: RunGroup[];
}

type ChipValue = string | string[]; // multiSelect 칩(features 등)은 string[]
```

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `activeProjectId` | `string?` | 아니오 | 현재 활성 프로젝트. 기계/세션 종속 — export에서 제외 |
| `selections` | `Record<projectId, Record<chipId, ChipValue>>` | 예 | 칩 선택 값. 값 자체가 아니라 "무엇을 골랐는지"만 저장(ADR-007) |
| `invocation` | `Record<projectId, Record<profileName, InvocationConfig>>` | 예 | 구성(profile)별 호출 오버레이. `profileName`은 `selections[projectId]['profile']`에서 옴 |
| `groups` | `RunGroup[]` | 예 | 워크스페이스 로컬 Run Group. profile export(F12)에 **포함되지 않음** |

- 프로젝트·구성별 독립 유지 — 전환해도 각자 마지막 상태 복원(INV-5).
- **로드 시 정규화(구현 반영)**: `StateStore`(`src/core/stateStore.ts`)가 누락 필드를 `{}` / `[]`로 기본값 처리 — 필드가 없던 시절에 저장된 상태도 마이그레이션 없이 읽힌다.
- `runArgs`는 구 `Record<projectId, string[]>` 위치에서 `InvocationConfig.runArgs`로 승격 — 구성별로 다르게 저장된다(ADR-011).

### 4.2 `InvocationConfig` (계층 ③ 오버레이)

캐노니컬 파일에 절대 기록되지 않으며, 빌드/실행 Task 생성 시점에만 주입된다.

```ts
type OptionValue = string | number | boolean | string[];

interface InvocationConfig {
  compiler?: Record<string, OptionValue>; // 카탈로그 옵션 id -> 값 (예: opt-level)
  linker?: Record<string, OptionValue>;
  outputDir?: string;                     // 출력 위치 (예: CARGO_TARGET_DIR)
  env?: Record<string, string>;           // 환경 변수 (예: PYTHONPATH)
  runArgs?: string[];                     // 프로그램 실행 인자 (F16, 승격 위치)
  preBuild?: string[];                    // 빌드/실행 전 명령 (ShellExecution)
  postBuild?: string[];                   // 빌드/실행 후 명령
}
```

### 4.3 `RunGroup` (구현 반영: v0.4.0 additive)

여러 프로젝트를 의존 순서대로 함께 시작하는 워크스페이스 로컬 정의(ADR-015). v1은 run 전용 멤버만 지원.

```ts
interface RunGroup {
  id: string;              // 안정 id (예: `group:<token>`) — 저장/삭제/조회 키
  name: string;            // 표시 이름
  members: RunGroupMember[];
}

interface RunGroupMember {
  projectId: string;       // 감지된 프로젝트의 ProjectInfo.id. 그룹 내 유일
  dependsOn: string[];     // 먼저 시작해야 하는 동일 그룹 멤버들의 projectId (자기참조·미해결 참조·순환 거부)
  readiness?: ReadinessProbe; // 준비 게이트 (MS-018/ADR-018). 생략 = 프로세스 spawn 시 준비 (ADR-015)
}

type ReadinessProbe =
  | { kind: 'port'; port: number; timeoutMs: number }                       // TCP connect 성공 시 준비
  | { kind: 'http'; url: string; expectStatus?: number; timeoutMs: number }; // GET이 기대 상태코드(기본 200) 반환 시 준비
```

## 5. 스키마 정의 — `ProfileExport` (export 파일)

파일명: `devswitcher.profile.json` (F12, 상세설계서 §6.3). 타입 SSOT: `src/core/types.ts`의 `ProfileExport`.

`PersistedState`의 두 맵(`selections` + `invocation`)을 그대로 담는다 — 직렬화가 곧 저장 스키마라 라운드트립에 변환 코드가 필요 없다(C-4 정합화, 2026-08-15).

```ts
const PROFILE_EXPORT_VERSION = 1;

interface ProfileExport {
  version: number;      // 1
  exportedAt: string;   // ISO 8601 타임스탬프
  selections: Record<string, Record<string, ChipValue>>;
  invocation: Record<string, Record<string, InvocationConfig>>;
}
```

예시:

```jsonc
{
  "version": 1,
  "exportedAt": "2026-08-15T12:00:00Z",
  "selections": {
    "cargo:crates/my-app/Cargo.toml": {
      "profile": "release", "architecture": "x86_64-pc-windows-msvc",
      "features": ["gui", "metrics"], "target": "main"
    }
  },
  "invocation": {
    "cargo:crates/my-app/Cargo.toml": {
      "release": { "runArgs": ["--config", "dev.toml"] }
    }
  }
}
```

### 5.1 포함/제외 규칙

| 항목 | export 포함 여부 | 사유 |
|------|-----------------|------|
| `selections` | 포함 | 기계 독립 projectId(ADR-006)라 팀/클론 간 그대로 공유 가능 |
| `invocation` | 포함 | `runArgs`는 승격 위치 `invocation[projectId][profile].runArgs`에 실림 |
| `activeProjectId` | **제외** | 기계/세션 종속 |
| `groups` | **제외** | 워크스페이스 로컬 오케스트레이션 — v1 export 대상 아님 |

### 5.2 Import 규칙 (구현: `src/core/profileExport.ts`)

- 파싱/버전/형태 오류(두 맵이 string-keyed 객체가 아님) → `DevSwitcherError('PROFILE_IMPORT_INVALID')`.
- 현재 스캔에 존재하는 projectId만 반영(applied), 나머지는 결과 요약에 skip 표시.
- 반영되는 프로젝트는 저장된 `selections`/`invocation`을 **프로젝트 단위로 통째 교체**(last-writer-wins). `activeProjectId`와 미언급 프로젝트, 기존 `groups`는 보존.
- 반영 후 reconcile(§8)로 매니페스트가 더 이상 제공하지 않는 칩 값을 정리(E10).

## 6. 캐노니컬 파일 (SSOT) — 언어별 데이터 원본

프로필·features·타깃 등 **값의 정의**는 각 언어의 캐노니컬 파일이 원본이다(ADR-007). 확장은 감지 글롭(`manifestGlobs`)으로 이 파일을 찾아 읽기만 하며, 절대 편집하지 않는다(ADR-013).

> 기준 문서 `data_model.md`는 Cargo(`Cargo.toml`)만 예시로 들지만, **구현 반영**: 현재 코드에는 6개 어댑터가 등록되어 있다(`src/adapters/`).

| 어댑터 id | 캐노니컬 파일 (감지 글롭) | 비고 |
|-----------|--------------------------|------|
| `cargo` | `**/Cargo.toml` | v1 원 실구현 대상 |
| `cmake` | `**/CMakeLists.txt` | `CMakePresets.json` 존재 시 Preset 칩 표시(TASK-041, `appliesTo`) |
| `dotnet` | `**/*.csproj` | |
| `python` | `**/pyproject.toml` | |
| `go` | `**/go.mod` | |
| `node` | `**/package.json` | |

## 7. 키 설계 (식별자)

| 키 | 형식 | 성질 |
|----|------|------|
| `projectId` | `${adapterId}:${워크스페이스 상대 manifest 경로}` (예: `cargo:crates/my-app/Cargo.toml`) | 기계 독립(ADR-006) — 클론 간 공유 가능. `selections`/`invocation`/`RunGroupMember`의 외래 키 역할 |
| `chipId` | 어댑터가 선언한 칩 id (`'profile'`, `'architecture'`, `'features'`, `'target'` 등) | `selections` 내부 키 |
| `profileName` | `selections[projectId]['profile']`의 값 | `invocation` 내부 키 — 구성(profile) 차원 |
| `RunGroup.id` | `group:<token>` 형태의 안정 id | 워크스페이스 로컬 |
| 저장 키 | `devSwitcher.state.v1` | 스키마 버전을 키에 포함(§9) |

관계 요약 (참조 무결성은 DB 제약이 아니라 재검증 로직 §8로 유지):

```text
PersistedState
 ├─ selections:  projectId ──> (chipId ──> ChipValue)
 ├─ invocation:  projectId ──> (profileName ──> InvocationConfig)
 ├─ groups[]:    RunGroup ──> members[].projectId ──(참조)──> 감지된 프로젝트
 └─ activeProjectId ──(참조)──> 감지된 프로젝트
```

## 8. 데이터 무결성 — 재검증 (reconcile)

DB 제약조건이 없으므로, 활성화·재스캔 시 저장 상태를 스캔 결과와 대조해 정합성을 유지한다(상세설계서 §6.2, 구현: `src/core/stateStore.ts` + `src/core/stateReconcile.ts`).

| 상황 | 처리 |
|------|------|
| 저장된 projectId가 스캔 결과에 없음 | 항목 유지하되 비활성(브랜치 전환 대비). 설계상 30일 초과 미사용 시 정리 — **미확정**(아래 참조) |
| 칩 값이 `listItems` 결과에 없음(프로파일 삭제 등) | 해당 값만 삭제 + 미선택 표시(E10). 제거된 (projectId, chipId) 쌍은 1회 토스트로 안내 |
| `activeProjectId`가 스캔 결과에 없음 | 스캔 결과 기준으로 재해석(`resolveActiveProject`) |
| import된 값이 매니페스트와 불일치 | import 반영 후 reconcile로 정리(§5.2) |

> **구현 반영 — 30일 정리 미구현**: 설계(`data_model.md` §3)는 30일 초과 미사용 항목 정리를 명시하나,
> 이를 위한 `lastUsed` 타임스탬프 필드가 `PersistedState`에 없어 구현이 이연된 상태다(스키마 추가 필요,
> `stateStore.ts` 주석 명시). — **미확정**

## 9. 마이그레이션 전략

| 버전 | 변경 | 호환성 |
|------|------|--------|
| v1 (`devSwitcher.state.v1`) | 초기 스키마. `invocation`은 배포된 선행 버전이 없어 초기 스키마에 포함(마이그레이션 불필요) | — |
| v1 내 additive 추가 (`groups`) | 새 키 없이 필드 추가 — `StateStore`가 로드 시 누락 필드를 기본값으로 정규화 | Backward (필드 없는 저장분 그대로 읽힘) |
| 향후 breaking 변경 | 새 키(`devSwitcher.state.v2`) 도입 + v1을 읽어 이관 | Backward (v1 읽기 유지) |

export 파일은 `version` 필드(현재 `1`)로 버전을 명시하며, 미지원 버전은 import 시 `PROFILE_IMPORT_INVALID`로 거부된다.

## 10. 가정 및 미확정 사항

### 가정 (Assumptions)
