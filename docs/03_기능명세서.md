## 1. 개요

본 문서는 DevSwitcher Tools의 기능 F1~F21이 실제로 어떻게 동작하는지 정의하는 공식 기능 명세서다.

- **기능 ID 체계**: 설계서의 `F1~F19` 번호 체계를 그대로 승계해 추적성을 유지하며, 이후 세션에서 F20(시작 마법사, ADR-010)·F21(호출 구성 오버레이, ADR-011·012)이 추가되었다.
- **명세 기준**: 상세 시퀀스·에러 처리는 상세설계서(`DevSwitcher-Tools_Detailed-Design.md`) 해당 절을 기준으로 하고, 본 문서는 구조화된 캐노니컬 명세로 유지한다.
- **관련 Intent**: INT-001

## 2. 범위 주석 — 초기 설계 범위와 v1.0.0 릴리즈 범위

> **[v1.0.0 주석]** 기준 문서는 **초기 v1 설계 범위** 기준으로 작성되었다: 스위치·빌드·디버그 실구현은 **CargoAdapter(Rust) 단독**이며, C++(CMake)/C#(dotnet)/Python은 칩 선언 스텁만 두고 액션 시 "지원 예정"을 안내(E8)하는 범위였다.
>
> **v1.0.0 릴리즈(2026-08-17) 시점에는 6개 언어(Rust · C++/CMake · C# · Python · Go · Node.js/TypeScript)로 F1~F20 전 기능 구현이 완료**되어 초기 설계 범위와 다르다. **v1.2.0(2026-08-19)에서 C++/Visual Studio 어댑터가 추가되어 7개 툴체인이 되었다**(시작 마법사 F20은 VS 미지원 — VS 프로젝트는 Visual Studio에서 생성). 본 문서의 각 명세에서 "v1은 Rust만", "스텁", "4개 언어" 등의 표현은 기준 문서의 초기 설계 범위 서술을 왜곡 없이 유지한 것이며, v1.0.0 현재 상태와 다른 부분은 해당 위치에 주석으로 표시했다.
>
> 단, **Go·Node.js/TypeScript 어댑터의 세부 명세**(감지 글롭, 칩 구성, 액션 명령, 시작 마법사 템플릿 등)는 기준 문서에 존재하지 않으므로 본 문서에서는 **'미확정'**으로 표시한다(§7). 또한 기준 문서에서 **v2 이월**로 명시된 세부(캐노니컬 파일 국소 편집 등)는 v1.0.0에서도 그대로 v2 이월로 유지한다.

> **[v1.0.0 주석]** 위 "초기 v1 설계 범위" 열은 기준 문서의 서술을 유지한 것이다. v1.0.0 현재는 F1~F20 전 기능이 6개 언어 기준으로 구현 완료되었다(§2). F11의 v1.0.0 세부 동작과 F21의 v1.0.0 구현 완료 여부·비(非)Rust 카탈로그 실데이터 여부는 기준 문서에서 확인되지 않아 미확정이다(§7).

**초기 설계 범위 관련 기준 문서 원 주석** (왜곡 없이 유지):

- v1 실구현은 스위치·빌드·디버그 기준 **CargoAdapter(Rust) 단독**. CMake/Dotnet/Python은 칩 선언 스텁만 두며, 액션 시 "지원 예정" 안내(E8). *→ v1.0.0 현재와 다름(§2).*
- 단, **F20(시작 마법사)은 예외** — 4개 언어 모두 v1 실동작한다(네이티브 init 호출은 단순해 전체 어댑터 실구현이 필요 없음). *→ v1.0.0 현재는 6개 언어 체계이나 Go·Node.js의 마법사 템플릿 명세는 미확정(§7).*
- **F21(호출 구성)**: 오버레이 저장·주입 프레임워크와 옵션 카탈로그 구조는 전 언어 공통이나, 실데이터(cargo 옵션 카탈로그·주입)는 v1 Rust만. 언어별 능력 매핑은 `interface_contract.md` §8.
- **범위 조정(v2 이월 — v1.0.0에서도 유지)**: 캐노니컬 파일 국소 편집(구 §8.7, `[profile.*]` 스칼라 쓰기)은 **v2로 이월** — v1은 파일을 읽기만 하고 호출 시점 주입(F21)으로 옵션을 적용한다(ADR-011).

## 3.1 v1.1.0 이후 추가 기능 상세 (F22~F26)

> 이 절은 v1.0.0 이후 릴리즈에서 추가된 기능이다. 기준 문서(`functional_spec.md`)의 F1~F21 서술은 위 §3에 원문 그대로 두고, 이후 변경은 여기에 누적한다.

### F22 — 언어 활성 필터 (v1.2.0)

`devSwitcher.languages.enabled`에 담긴 어댑터 id 목록이 **스캔·감지·새 프로젝트 생성**의 대상을 정한다. 설정 페이지 General 탭의 체크박스가 같은 설정을 편집하며, 값이 바뀌면 자동 재스캔한다.

- **Fail-open**: 빈 목록이나 알 수 없는 id만 든 목록은 "전체 활성"으로 해석한다. 설정 오타로 스위처가 통째로 비는 것보다 낫다.
- `adapterFor`/`adapter`는 필터를 적용하지 않는다 — 설정 변경 도중에도 이미 목록에 있는 프로젝트가 계속 해석돼야 하기 때문이다.

### F23 — Visual Studio 어댑터 (v1.2.0, ADR-021)

7번째 툴체인. `.sln`/`.slnx`/`.vcxproj`를 감지해 MSBuild로 빌드하고, cppvsdbg로 디버그한다. **Windows 전용.**

- **CMake 생성물 제외**: 빌드 디렉토리에 CMake가 써 놓은 `.sln`/`.vcxproj`는 `CMakeCache.txt` 마커로 걸러낸다. 그렇지 않으면 CMake 프로젝트 하나가 스위처에 두 번 나타난다.
- **`.csproj`는 dotnet 어댑터 소유**로 유지한다(A안) — vs 어댑터는 `.vcxproj`만 가져간다.
- 칩은 **Configuration**(profile)·**Platform**(architecture) 둘. 솔루션은 루트 계층, `.vcxproj`는 하위 계층(ADR-019 재사용).
- 실행 경로는 추측하지 않고 `MSBuild -getProperty:TargetPath`로 **평가해서** 얻는다(DD-05). 솔루션 빌드와 단독 빌드의 출력 경로가 갈라지므로 멤버 프로젝트에는 `/p:SolutionDir`을 주입한다.
- static library 타깃은 `validateAction`이 run/debug를 차단한다(build-only).

### F24 — 부작용 없는 칩 질의 `probe: false` (v1.2.1 / v1.3.0)

`ChipDescriptor.listItems`/`defaultValue`가 받는 `opts.probe`는 **"부작용이나 비용이 있는 작업 없이, 이미 아는 것만 답하라"**는 요청이다.

- `probe: false`로 묻는 경로: 프로젝트 **전환**(`applyDefaults`), **활성화·재스캔의 정합성 패스**(`gatherValidItems`), **설정 페이지 렌더**(칩 뷰·프로젝트 카드).
- `probe`를 붙이지 않고 묻는 경로: 칩 **피커**, **빌드/실행/디버그 직전 시딩**(`ensureRequiredChips`), Run Group 멤버 시딩. 이때는 사용자가 명시적으로 요청한 것이므로 실제 조회가 정당하다.
- **빈 답은 "답 없음"으로 취급한다.** 빈 목록을 "유효 항목이 하나도 없음"으로 읽으면 정합성 패스가 사용자의 저장된 선택을 지워버린다.
- 어댑터별 대응(v1.3.0에서 전 어댑터로 확대):

| 어댑터 | `probe: false`가 막는 것 |
|--------|--------------------------|
| cmake | `cmake -S -B` **configure** — 소스 디렉토리에 빌드 트리를 쓰는 행위 |
| dotnet | `dotnet msbuild -getProperty` 프로세스 |
| cargo | `cargo metadata` · `rustup target list` 프로세스 |
| go | `go list` 프로세스 |
| python | 후보 인터프리터마다 1개씩 뜨던 프로브 프로세스 |
| vs · node | 해당 없음 — 매니페스트 파일 1회 읽기라 비용이 없다 |

> cmake 외의 어댑터는 **파일을 만들지 않았다**(빈 사본에서 실행해 실증). 따라서 이들의 수정은 결함 제거가 아니라 **비용·정합성** 개선이다.

### F25 — 스캔 제외 폴더 (v1.3.0)

`devSwitcher.scan.exclude`에 등록한 폴더는 스캔이 건너뛴다. 폴더명(`vendor`)이나 글롭(`**/examples/**`)을 쓴다.

- 저장 위치는 `.vscode/settings.json`(팀 공유) 또는 User 설정(개인 규칙).
- **User ∪ Workspace 합집합.** 제외 규칙은 본질적으로 가산적이라, 워크스페이스 설정이 개인 규칙을 덮어써서는 안 된다(`get()` 대신 `inspect()`).
- **`!` 재포함은 미지원**이며, `!` 항목은 반쯤 적용하지 않고 **버린다**. 순서 의존·우선순위·중첩 상속이 따라붙는 지점이다.
- 결합된 패턴은 **최상위 중괄호 목록**이다. 기존 코드는 경로 안쪽 중괄호만 썼기에 이 형태는 실 VSCode 호스트 통합 테스트로 검증한다.

### F26 — Clean / Delete Build Tree (v1.3.0)

VSCode의 Task 그룹에는 `build`/`test`만 있고 `clean` 개념이 없다. 두 기능은 **효과가 다르므로 분리한다.**

| | Clean | Delete Build Tree |
|---|-------|-------------------|
| 지우는 것 | 빌드 **산출물** | 빌드 **디렉토리 자체** |
| CMake 기준 | `CMakeCache.txt`·`.cmake/api/` **남음** | 통째로 사라짐 |
| 용도 | 일상 정리 | v1.2.1 이전에 오염된 트리 원상복구 |
| 지원 | cargo·cmake·vs·dotnet·go | cargo·cmake·dotnet |

- **범위는 어댑터가 선언하고 UI는 나열만 한다** (`CleanScope[]` — 칩과 같은 모델, INV-2 유지). "clean"의 의미가 툴체인마다 다르므로 하나를 골라 나머지를 틀리게 만드는 대신, **각 어댑터가 실제로 할 수 있는 것만** 내놓고 각 항목이 **무슨 명령을 돌려 무엇을 지우는지** 설명을 단다.

| 어댑터 | 제공 범위 |
|--------|-----------|
| cargo | `cargo clean -p <pkg>`(이 패키지) · `cargo clean`(워크스페이스 전체) — **후자는 멤버가 2개 이상일 때만** 노출(단일 패키지에선 둘이 같아 잡음) |
| cmake | **1개뿐** — `--target clean`은 트리 전체이고 CMake에 타깃별 clean이 없다. 하위 프로젝트 선택 시 "이 트리는 루트의 것이며 형제 프로젝트와 공유된다"를 명시 |
| vs | `.vcxproj` = 이 프로젝트 · (솔루션 멤버면) 솔루션 전체 / `.sln` = 솔루션 전체 1개 |
| dotnet | 1개 — `dotnet clean`은 이미 프로젝트 스코프. 빌드와 같은 `-c`/`-f`/`-r`를 넘겨 **빌드가 만든 출력**을 지운다 |
| go | 선택 패키지 · 모듈 전체(`./...`) — 단, 컴파일 산출물은 GOCACHE(모듈 밖)라 실제로 지워지는 양이 적다는 점을 설명에 명시 |

  범위가 1개인 어댑터에서도 피커를 띄운다. **무엇이 사라지는지가 어댑터마다 다른 바로 그 지점**이고, 설명을 읽는 자리가 피커이기 때문이다.
- **삭제 후보도 같은 원칙이다.** `buildTreeDirs`는 경로 문자열이 아니라 `{path, description}`을 돌려주고, 확인 모달이 경로 밑에 그 설명을 붙인다. 경로만으로는 `<project>/build`와 `<root>/build`를 구분할 수 없다.
- **진입점은 명령 팔레트뿐이다.** 삭제는 오클릭 비용이 커서 단축키·상태바 버튼을 두지 않는다.
- node/python은 표준 clean 명령이 없어 `actions.clean = false`다. node의 `clean` 스크립트는 프로젝트마다 있고 없고가 갈리는데 `actions`는 정적 선언이라 표현할 수 없다.
- go는 GOCACHE(모듈 밖)에 쓰므로 삭제할 트리가 없고, vs는 MSBuild 출력이 `$(Platform)/$(Configuration)`과 솔루션 레벨로 갈려 **경로를 추측하지 않는다**(DD-05).
- **어느 경로도 `prepareInvocation`을 호출하지 않는다.** CMake에서 그것은 configure이고, clean 요청이 빌드 트리를 만들어내면 v1.2.1이 막은 결함이 그대로 돌아온다. 미구성 트리는 "정리할 것 없음"으로 답한다.
- 삭제 안전장치(`core/cleanPlan.ts`, 순수 함수): 워크스페이스 밖·워크스페이스 루트 자신·**프로젝트 소스 디렉토리 자신**·상대경로를 거부하고, 남은 경로를 **전부 전문 그대로** 모달에 나열한 뒤, 지원하는 플랫폼에서는 휴지통으로 보낸다.

## 4. 핵심 기능 상세

### 4.1 F1 — 프로젝트 자동 감지

| 항목 | 내용 |
| --- | --- |
| 관련 요구사항 | FR-001 |
| 우선순위 | P1 |

**기본 흐름**

1. `activate()`에서 모든 `workspaceFolder` × 모든 어댑터의 `manifestGlobs`로 글롭 스캔(`workspace.findFiles('**/Cargo.toml', '**/target/**')`).
2. 루트 매니페스트가 `[workspace]`면 `cargo metadata`가 멤버 전체를 반환 → 멤버 패키지 각각을 `ProjectInfo`로 등록.
3. 독립 매니페스트면 단일 `ProjectInfo`. `ProjectInfo.id = ${adapterId}:${상대경로}`.
4. 멀티루트는 폴더별 반복. 중복 발견 시 workspace 쪽으로 병합.

**예외 흐름**

- 프로젝트 0개 → 상태바 미표시, watcher는 유지(E3).
- 툴체인 미설치 → 경고 칩(E1).

**검증 기준**

- 단일 패키지·cargo workspace(멤버 N)·멀티루트에서 프로젝트가 정확히 열거된다.
- `target/` 하위 매니페스트는 제외된다.

> **[v1.0.0 주석]** 위 흐름은 Rust(Cargo) 기준 서술이다. 다른 언어 어댑터의 감지 글롭·메타데이터 조회 세부는 기준 문서에 없어 미확정(§7).

### 4.2 F2 — 프로젝트 스위처

**기본 흐름**: 프로젝트 칩 클릭 → QuickPick으로 감지된 전체 프로젝트(언어 무관) 나열 → 선택 시 활성 프로젝트 전환 → `StateStore`에서 해당 프로젝트의 마지막 선택 복원 → 상태바 재렌더링.

**후행 조건**: 프로젝트별 선택 상태가 독립 유지된다(Rust ↔ C++를 오가도 각자 기억).

### 4.3 F3 — 어댑터 능력 선언 (칩 프레임워크)

**규칙**: 상태바는 활성 어댑터의 `chips: ChipDescriptor[]`를 **순회**하며 그린다. 어댑터를 추가·변경해도 상태바/QuickPick/설정 패널 코드는 수정하지 않는다.

**리트머스**: PythonAdapter는 profile·architecture·build 칩을 선언하지 않고 environment 칩을 선언한다 → 칩 구성이 선언대로 바뀌면 프레임워크가 검증된 것(DoD 6).

### 4.4 F5 / F8 — 액션 오케스트레이션 (빌드/실행/디버그)

- **빌드**: required 칩 검증 → `adapter.createBuildTask()` → `TaskRunner.run()`(Task API, 종료 코드 감지) → 실패 시 Problems 포커스 제안.
- **실행**: required 칩 검증 → `createRunTask()`(cargo run은 빌드 포함) → 실행.
- **디버그(상세 §7.4)**: required 칩 검증 → 필수 확장(CodeLLDB) 온디맨드 확인 → 빌드 Task 실행(실패 시 중단, E5) → `resolveExecutable()`로 실행 파일 경로 해석(DD-05) → `createDebugConfig()` → `vscode.debug.startDebugging()`.

**검증 기준**

- 고의 컴파일 에러 시 Problems 패널에 진단이 표시되고(problem matcher), 종료 코드로 실패가 감지된다.
- 빌드 실패 시 디버그가 중단된다.
- 디버그 시 runArgs가 전달된다.

### 4.5 F6 — 상태·에러 표시

| 상태 | 상태바 표현 |
| --- | --- |
| 프로젝트 0개 | 칩 전체 미표시 |
| 툴체인 미설치 | 경고 칩 1개 → 클릭 시 Doctor |
| 매니페스트 파싱 실패 | 프로젝트 칩 errorBackground, 마지막 정상 캐시로 계속 동작 |
| required 칩 미선택 | warningBackground, 액션 시 해당 QuickPick 먼저 표시 |
| 작업 진행 중 | 액션 버튼 `$(sync~spin)` + disabled (중복 실행 방지) |

### 4.6 F17 — 매니페스트 감시

**흐름**: `FileSystemWatcher`가 `manifestGlobs` 감시 → create/change/delete 이벤트 → 500ms 디바운스 → 해당 어댑터 `invalidateCache()` → 변경된 workspaceFolder만 재스캔 → `reconcile()` → 상태바 갱신. `target/`, `node_modules/`는 제외. 확장은 캐노니컬 파일을 편집하지 않으므로(ADR-013) 재스캔 트리거는 외부 편집·F20 생성뿐이다.

**수동 재스캔**: 감시가 놓치는 변경(폴더 이동/이름변경, VCS 체크아웃, 편집기 밖 파일 조작)에 대비해 명령 `DevSwitcher: Rescan Projects`(`devSwitcher.rescan`)로 강제 갱신을 제공한다 — 전 어댑터 캐시 무효화 + 재스캔 + reconcile + 툴체인 재점검 + 결과 개수 토스트.

### 4.7 F19 — 환경 진단·의존성 처리 (Doctor)

**원칙**: 우아한 성능 저하(graceful degradation) — 없는 것에 의존하는 기능만 비활성화하고 복구 경로를 항상 제시한다.

**3단계 처리**

1. **완전 자동**: 확장 설치, `rustup target add`
2. **반자동**: 툴체인 설치 명령 대행
3. **안내만**: WSL 본체, Docker Desktop

**Doctor 명령**: 활성 어댑터 전제조건 일괄 점검 + 항목별 해결 액션(QuickPick). 진입점은 명령 팔레트, E1 경고 칩, 온디맨드 설치 취소의 세 곳이다.

### 4.8 F20 — 새 프로젝트 시작 마법사

| 항목 | 내용 |
| --- | --- |
| 관련 요구사항 | FR-013 |
| 관련 ADR | ADR-010 |
| 우선순위 | P1 |

**기본 흐름**

1. 명령 `DevSwitcher: 새 프로젝트 시작`(`devSwitcher.newProject`)을 **수동 호출**한다.
2. 대상 **부모 폴더 선택** — 네이티브 폴더 선택창(기본=워크스페이스 루트, 하위 폴더 자유 선택 예: `services/`·`apps/`). 스캔 감지를 위해 워크스페이스 내부로 제한한다.
3. 언어 QuickPick: Rust / C++ / C# / Python.
4. 해당 어댑터가 네이티브 도구로 **기본 템플릿 생성에 위임**한다:
   - Rust → `cargo new` (또는 `cargo init`)
   - C# → `dotnet new console`
   - C++ → cmake 최소 템플릿(`CMakeLists.txt` + `main`)
   - Python → 기본 `pyproject.toml`
5. 생성 후 ManifestWatcher(F17)가 새 매니페스트를 감지 → 스위처에 자동 등장 → 상태바 렌더.

> **[v1.0.0 주석]** 기준 문서의 언어 QuickPick·템플릿 목록은 4개 언어(Rust/C++/C#/Python) 기준이다. v1.0.0은 6개 언어 체계이나, Go·Node.js/TypeScript의 마법사 진입 여부와 템플릿 생성 명령은 기준 문서에 없어 미확정(§7).

**특이사항**

- 초기 v1 설계에서도 **전 언어 실동작** — 스위치/빌드/디버그가 Rust 단독인 것과 달리, 시작 마법사는 4개 언어 모두 동작(네이티브 init 위임이 단순).
- 트리거는 **수동 호출만** — 빈 폴더 자동 감지·자동 제안 없음.
- 네이티브 도구(cargo/dotnet/cmake/python) 부재 시 → Doctor/온디맨드 안내로 연결(F19 경로 재사용).

**검증 기준**

- 빈 폴더에서 명령 호출 → 언어 선택 → 매니페스트 생성 → 스위처 자동 등장.
- 각 언어가 네이티브 기본 템플릿으로 생성된다.
- 네이티브 도구 부재 시 Doctor 안내로 연결된다.

### 4.9 F21 — 호출 구성 오버레이 + 설정 페이지

| 항목 | 내용 |
| --- | --- |
| 관련 요구사항 | FR-014 |
| 관련 ADR | ADR-011(오버레이), ADR-012(설정 페이지·카탈로그) |
| 관련 US | US-010, US-012 |
| 우선순위 | P2 |

**개념**: VS2026식 "프로젝트 속성"(출력 위치/이름, 컴파일러/링커 옵션, 환경변수, 빌드 전/후 이벤트)을 **캐노니컬 파일을 편집하지 않고** `(프로젝트 × 구성)`별로 저장했다가, 빌드/실행 호출 시 `--config`/env/flag로 **대신 주입**한다. "중계가 명령을 조립해 대신 실행"하는 모델(F16 runArgs의 일반화).

**설정 페이지 (ADR-012)**

- 형태: `WebviewPanel`(에디터 탭) = "설정 페이지" — 모달 다이얼로그가 아니다. VS 속성 페이지 메타포.
- 레이아웃: 상단 `프로젝트 / 구성(profile)` 스위처 → 좌측 카테고리 → 중앙 상세(설명·예제·허용값·기본값) → 값 에디터(타입 인식) → 하단 **적용 명령 미리보기**.
- 옵션 브라우저: 개발자가 옵션을 몰라도 되도록 **목록 + 설명 + 예제 + 값 에디트**를 제공. enum은 드롭다운, bool은 토글, 숫자/텍스트는 입력.
- 카탈로그·카테고리는 **어댑터가 선언**(번들 데이터) → UI는 언어를 모른다(ADR-003의 연장). Python(build=false)은 컴파일러/링커/출력 카테고리를 표시하지 않는다(리트머스).

**기본 흐름 (빌드 시)**

1. 활성 `(프로젝트, 구성)`의 `InvocationConfig` 오버레이를 StateStore에서 로드.
2. 어댑터가 빌드 Task 조립 시 오버레이를 언어별로 접어 넣음(cargo `--config`/env, dotnet `-p:`, cmake `-D`, python env).
3. 전(pre) 명령이 있으면 먼저 실행 → 빌드 Task → 후(post) 명령. (`ShellExecution`, NFR-002 예외)
4. 설정 페이지 미리보기와 실제 실행 명령이 일치한다.

**언어별 능력**: `interface_contract.md` §8 표를 SSOT로 한다. 요지 — Rust는 빌드 시점 `--config`/RUSTFLAGS로 폭넓게 주입(v1 실데이터), cmake는 configure/build 2단계(v2), dotnet은 `-p:`(v2), python은 env·PYTHONPATH·실행 인자 중심(build 없음).

**범위·경계**

- **v1 = 주입만**. 오버레이를 캐노니컬 파일에 영구 반영(편집/승격)하는 것은 **v2**(구 §8.7). *v1.0.0에서도 v2 이월 그대로 유지.*
- 초기 v1 설계의 실데이터는 cargo 옵션 카탈로그·주입만이며, 나머지 어댑터는 카탈로그 스텁. *→ v1.0.0에서 비(非)Rust 카탈로그 실데이터 제공 여부는 미확정(§7).*
- 오버레이는 DevSwitcher 호출에만 적용된다(수동 터미널 빌드에는 미적용) — 설계된 동작.

**검증 기준**

- 같은 프로젝트에서 Debug/Release 구성별로 다른 컴파일 옵션·runArgs·env가 저장·주입된다.
- 설정 페이지에서 옵션 선택 시 설명·예제가 표시되고, 값 변경이 하단 명령 미리보기에 반영된다.
- 미리보기 명령과 실제 실행 명령이 일치한다.
- 빌드 전/후 명령이 순서대로 실행된다.
- Python 어댑터는 컴파일러/링커/출력 카테고리를 표시하지 않는다(리트머스).
- 캐노니컬 파일(`Cargo.toml`)은 이 기능으로 수정되지 않는다(v1).

| F9 타깃 | bin 타깃 + examples, `required` 칩, bin 1개면 자동 선택 | 미선택 시 액션 전 QuickPick 유도(E4) |
| F10 아키텍처 | 설치+미설치 target 열거, 미설치 선택 시 `rustup target add` 확인 실행 | 축약 표시(`x86_64-pc-windows-msvc` → `x64-msvc`), tooltip에 전체값 |
| F12 export/import | `devswitcher.profile.json`, projectId 기계 독립 | 라운드트립 + 다른 클론에서 import 시 존재하는 것만 반영 |
| F13 problem matcher | `$rustc` 우선, 자체 정의 폴백 | 진단이 Problems에 표시, Rerun Last Task 호환 |
| F15 features | multiSelect, `default` 처리(`featuresToArgs`) | default 해제 → `--no-default-features`, 조합 → `--features a,b` |
| F16 run args | 실행/디버그 시 `--` 뒤 프로그램 인자 | `parseArgsLine()` 따옴표 토큰화 |
| F18 원격 | `extensionKind: ["workspace"]`, Uri 기반 경로, cargo가 경로 해석 | WSL에서 F1~F5 동일 동작, 창별 선택 상태 독립 |

> **[v1.0.0 주석]** 위 표의 세부(예: `cargo`·`rustup`·`$rustc`)는 Rust 어댑터 기준 명세다. 다른 언어 어댑터에서의 대응 동작은 기준 문서에 정의되어 있지 않다(§7).

## 6. 파일 의존성 및 부재·손상 처리 (Graceful Degradation)

**원칙**: 없는 것이 있어도 확장은 죽지 않고, 그것에 **의존하는 기능만** 비활성화하며 복구 경로를 항상 제시한다(상세 §13.1). 확장은 선택적 설정 파일(`settings.json`/`launch.json`)을 **필수로 요구하지 않는다**.

### 6.1 파일 의존성 (v1/Rust 기준)

| 파일 | 필요성 | 부재 시 | 근거 |
|------|--------|---------|------|
| `Cargo.toml` (매니페스트) | 감지 기준(사실상 필수) | 프로젝트 0개 → 상태바 침묵, watcher 유지 → 생성 시 자동 등장 | E3 |
| `.vscode/settings.json` | 불필요 | 동작 설정은 declared default, 선택 상태는 workspaceState | DD-01 |
| `.vscode/launch.json` | 불필요 | debug 구성을 프로그램적으로 생성 | DD-05 |
| `devswitcher.profile.json` | 선택(F12) | import하지 않으면 영향 없음 | §6.3 |
| cargo/rustup 툴체인 | 실행 필요 | 경고 칩 → Doctor 2단계 | E1 |
| CodeLLDB | 디버그 필요 | 온디맨드 설치 | E7 |
| rustup target | 크로스빌드 필요 | `(미설치)` 표기 + `rustup target add` | §13.4 |

### 6.2 부재 vs 손상 구분

- **부재**(파일 없음): 매니페스트 없음 → 침묵(E3).
- **손상**(있지만 파싱 실패): 마지막 정상 캐시 유지 + errorBackground + Output에 stderr, 저장 시 재시도(E2).
- **값 소멸**(캐노니컬 파일에서 선택 값이 삭제됨): `reconcile`로 해당 값만 제거, 미선택 표시(E10).

### 6.3 부재 시 능동 복구 (F20, ADR-010)

매니페스트가 없는 빈 폴더에서는 명령 `DevSwitcher: 새 프로젝트 시작`(F20)으로 언어를 골라 네이티브 도구(`cargo new` 등)로 기본 템플릿을 생성한다. 즉 **도구 부재(Doctor)처럼 매니페스트 부재도 능동 복구 경로가 있다** — 비대칭 해소. 단, 자동 제안 없이 **수동 호출**이며 파일 생성은 네이티브 도구에 위임한다(확장은 직접 스캐폴드하지 않음).

**검증 기준**

- `settings.json`/`launch.json` 없이 감지·칩·빌드·실행·디버그가 동작한다.
- 매니페스트 부재(E3)와 손상(E2)이 서로 다르게 처리된다.
- 매니페스트 부재 폴더에서 F20으로 새 프로젝트를 시작할 수 있다.
