## 1. 개요

DevSwitcher Tools v1.0.0의 검증은 두 축으로 수행되었다.

- **자동 테스트**: 순수 코어 로직 단위 테스트(mocha, vscode 무의존)와 실제 VSCode 호스트에서 실행되는 통합 스모크 테스트(`@vscode/test-electron`). v1.0.0 기준 **단위 268개 · 통합 3개**.
- **수동 테스트**: 상세설계서 §15.2의 수동 체크리스트를 기반으로 한 F5(Extension Development Host) 검증 24건(TC-01~TC-24). 각 케이스의 실행 근거는 세션 로그와 Milestone 기록으로 추적된다.

관련 문서: Intent INT-001, Milestone MS-001~018, 테스트 전략 `test_strategy.md`, 검증 증적 `verification_evidence.md`.

>
> **F5에서 실제로 잡힌 결함 3건** (전부 수정·재검증 완료):
> 1. **워크스페이스 멤버의 빌드 트리를 못 찾음** — cargo는 `target/`을 워크스페이스 루트에 두는데 `<package>/target`을 조합했다. `cargo metadata`의 `target_directory`를 쓰면 되는 문제였고, **ADR-005/DD-05가 이미 정해둔 규칙을 이 호출부만 안 따르고 있었다.**
> 2. **Clean이 선택된 아키텍처를 무시** — `--target` 미전달로 `target/<triple>/` 빌드가 살아남았다. dotnet·vs에는 "빌드와 같은 축" 규칙을 적용해놓고 cargo만 빠졌다.
> 3. **모달·피커가 긴 경로와 경고를 가운데서 잘랐다** — "지울 경로를 전부 보여준다"는 안전장치가 형식만 남고 실질을 잃은 경우. 삭제 가능 경로는 이미 워크스페이스 내부로 제한되므로 **상대경로 표시**로 해결했다(워크스페이스 밖 경로는 절대 축약하지 않는다 — 그게 위험 신호이므로).
>
> 셋 다 **화면이 아니라 파일시스템·실행 명령을 대조해서** 드러났다. 1번과 2번은 화면상 "정상 완료"로 보였다.
>
> **검증 시 주의(v1.2.1·v1.3.0에서 실제로 겪은 함정 2가지):**
> 1. 빌드 산출물은 gitignore 대상이라 **화면상 변화가 없다.** `find`로 파일시스템을 직접 확인해야 한다.
> 2. 관측된 파일 변경의 **출처를 확인해야 한다.** `--disable-extensions` 없이 띄운 Dev Host에서는 C# Dev Kit이 design-time build로 dotnet 픽스처의 `obj/`에 파일을 쓴다 — 우리 것이 아니다.
